## 1. この計画の目的

「たばコン」を、単に動く試作版ではなく、次の条件を満たす公開版へ仕上げる。

1. 砂を削る操作が気持ちよく、階段状の地形で理不尽に詰まりにくい。
2. 🚬がボールとして自然に落ち、転がり、ぶつかり、止まる。
3. 10ステージが名前だけでなく、地形・分岐・仕掛け・危険の置き方で明確に異なる。
4. どのステージでも20個到達を狙え、共通ランキングで極端な有利不利がない。
5. 動かせる🚬がなくなった場合に、制限時間いっぱいまで待たされない。
6. 処理落ち、バックグラウンド移動、通信失敗、連続リトライで結果が壊れない。
7. iPhone SE相当の小画面からiPad Proまで、横スクロールなしで遊べる。
8. ランキング送信に失敗しても結果画面、再挑戦、シェアが使える。
9. 公開時にsecret keyや管理用キーが含まれず、共通RPCだけを使う。
10. 文書、コード、公開ページ、Supabase登録、実験場表示が一致する。

# 6. PR3: ボール物理の安定化

## 6-1. 目的

🚬を、フレームレートや端末性能に左右されにくいボールとして動かす。平面で震え続けず、🚬同士が重ならず、見た目と判定が一致する状態を作る。

## 6-2. 対象

原則:

```text
index.html
docs/SPEC.md
docs/IMPLEMENTATION_PLAN.md
docs/REVIEW_CHECKLIST.md
```

この段階では砂グリッド、ステージ定義、スコア、ランキング、デザインを変更しない。

## 6-3. 固定間隔の物理更新

表示更新と物理更新を分ける。

```js
const PHYSICS_DT = 1 / 120;
const MAX_PHYSICS_STEPS = 6;
const MAX_ACCUMULATED_TIME = PHYSICS_DT * MAX_PHYSICS_STEPS;
```

- `requestAnimationFrame` は描画の入口として維持する。
- 実経過時間を物理蓄積値へ足す。
- 1回の表示で最大6回まで物理を進める。
- それ以上の遅れは切り捨て、復帰直後の暴走を防ぐ。
- 制限時間はPR2の絶対期限方式を維持する。
- 成功演出中は物理蓄積値を進めない。

期待する処理順:

```text
実時間同期
→ 成功演出確認
→ 固定間隔で仕掛け更新
→ 固定間隔で🚬更新
→ ボール同士の衝突
→ 終了判定
→ パーティクル更新
→ HUD更新
→ 描画
```

## 6-4. 半径の統一

現在の物理半径と描画半径の差をなくす。

仮決めではなく、PR3の正式値として次を使う。

```js
const BALL_RADIUS = 8;
const BALL_DRAW_RADIUS = 9;
const BALL_SHADOW_RADIUS = 10;
```

- 地形、仕掛け、トラップ、ゴール、ボール同士の判定は `BALL_RADIUS` を使う。
- 色付き円の本体は半径9以内。
- 影だけ半径10まで許す。
- 見た目と当たり判定の差を1px以内にする。
- 現在の各🚬の `r: 7` 直書きを廃止する。

## 6-5. 初期配置の間隔

半径統一とボール同士の衝突追加に合わせ、初期配置の重なりをなくす。

- 1クラスタ10個は5列×2行。
- 横間隔は17px以上。
- 縦間隔は17px以上。
- 左・中央・右クラスタ同士を重ねない。
- 外壁、砂、固定壁、危険ゾーン、仕掛け内部へ初期配置しない。

## 6-6. 🚬同士の衝突

30個なら最大435組なので、全組判定を採用してよい。

各固定物理更新で次を行う。

1. active同士だけを見る。
2. 中心距離が半径合計未満なら重なりを解消する。
3. 接近中の場合だけ速度へ反発を入れる。
4. 接線方向へ弱い摩擦を入れる。
5. 同じ位置の場合は、IDに基づく固定方向で分離し、ランダム震えを入れない。

推奨値:

```text
位置補正率: 0.8
許容重なり: 0.1px
反発: 2個のbounceの小さい方を上限にする
衝突解決反復: 2回/物理更新
```

球種ごとの質量は、ボール同士の衝突だけに使う。

```text
normal: 1.00
red: 1.25
blue: 0.80
black: 1.10
```

既存の重力・跳ねやすさの特徴は維持する。

## 6-7. 休止状態

低速で安定しているボールを毎回動かさず、震えと負荷を減らす。

追加状態:

```text
sleeping
sleepTimer
```

休止条件:

- 接地中
- 速度が3px/秒未満
- 0.6秒以上継続
- ローター、バー、ゲートへ接触していない

復帰条件:

- 近くの砂が削られた
- 他の🚬から一定以上の衝撃を受けた
- バー、ゲート、ローターへ接触した
- 接地セルがなくなった

休止中でもゴール、危険ゾーン、最下部判定は破綻させない。

## 6-8. 地形すり抜け防止

固定間隔だけで不十分な高速移動に備える。

- 物理更新前の位置を保存する。
- 1回の移動距離が `BALL_RADIUS * 0.5` を超える場合、最大4分割して移動・地形判定する。
- 速度へ上限を設ける。仮の上限は900px/秒。
- 壁外へ出た場合は、位置を世界内へ戻して速度を減衰する。

## 6-9. バー接触

毎フレーム小さく跳ね続けないようにする。

- 強く落下した最初の接触だけ軽く反発する。
- 低速で上面に接触した場合は `vy = 0` へ寄せる。
- バー速度の一部を横速度へ伝える。
- バー端では自然に落ちる。
- 同じ接触中に毎フレーム反発を追加しない。

追加状態候補:

```text
barContactId
barContactTime
```

## 6-10. ローター接触

現在の接線速度に基づく方向性を維持する。

- 接触位置が先端に近いほど強くする。
- 回転速度と回転方向を使う。
- 同一接触中に毎フレーム力を足し続けない。
- 50ms程度の接触待ち時間を設ける。
- 中心付近では過剰に飛ばさない。

## 6-11. PR3の禁止事項

- 砂解像度を変えない。
- ステージ配置を変えない。
- 成功条件を変えない。
- スコア式を変えない。
- Supabaseを変えない。
- 画面デザインを変えない。
- 10ステージ一巡方式を先に入れない。

## 6-12. PR3の合格条件

- 30fps、60fps、120Hz表示で物理結果が極端に変わらない。
- 平らな場所で1秒以上細かく震え続けない。
- 🚬同士が大きく重ならない。
- 30個を同時に流しても処理が止まらない。
- バー上で永久に跳ね続けない。
- 高速落下で薄い壁を明らかにすり抜けない。
- 見た目と判定の差が1px以内。
- 20個到達時の結果固定、即失敗、ランキング1回送信を壊していない。

## 6-13. PR3の戻し方

- 物理定数と新しい物理関数を1PR内へ閉じ込める。
- ステージデータと砂データを変更しない。
- 問題があればPR3だけをrevertできる状態にする。

# 7. PR4: 砂の細分化と地形描画の軽量化

## 7-1. 目的

砂を削った跡の階段感を減らし、🚬がセル角へ不自然に引っかかりにくくする。同時に、細かくした砂を毎フレーム大量描画せず、iPhoneで安定させる。

## 7-2. 2種類のグリッド

ステージ設計用の座標は、既存データを壊さないため48×144のまま残す。

```js
const LEVEL_GRID_W = 48;
const LEVEL_GRID_H = 144;
```

砂と固定壁の実処理用グリッドは、次を第一候補とする。

```js
const TERRAIN_GRID_W = 64;
const TERRAIN_GRID_H = 192;
```

1セルは約5×5pxになる。

実装前に、64×192版と現状48×144版を同じステージで比較する。iPhone 11 Pro相当で30fpsを下回る場合は、56×168も比較候補にする。性能を測らず64×192へ固定しない。

## 7-3. 砂と固定壁の分離

現在の1つの数値グリッドを、役割別に分ける。

```text
sandGrid: 削れる砂
wallGrid: 削れない固定壁
```

- 両方とも `Uint8Array` を使う。
- セルごとのオブジェクトを作らない。
- 砂崩れは `sandGrid` だけを動かす。
- 固定壁を砂崩れで動かさない。

## 7-4. ステージ座標の変換

48×144のステージ定義を、地形グリッドへ変換する関数を1か所にまとめる。

```text
levelCellToTerrainX
levelCellToTerrainY
levelRectToTerrainRect
```

各ステージデータへ64×192の値を直接重複記載しない。

## 7-5. 砂削りのまとめ処理

現在のスワイプ補間点ごとに砂崩れを繰り返す方式をやめる。

1回の入力移動で次を行う。

1. スワイプ線上の削除対象セルをまとめて空にする。
2. 変更範囲を1つの矩形へまとめる。
3. 砂崩れを1回だけ実行する。
4. 変更範囲の地形画像だけ更新する。
5. パーティクル数を上限内でまとめて生成する。

## 7-6. 砂崩れの保護領域

砂の移動先が次と重なる場合、そこへ砂を移動しない。

- activeな🚬の円
- 🦊のゴール内部と入口
- 危険ゾーン内部
- バーの矩形
- 閉じたゲートの矩形
- ローター中心とブレード周辺
- 世界最下部の消失帯

保護判定は毎セルで大量のオブジェクトを作らず、数値比較で行う。

## 7-7. 砂崩れの再現性

左右どちらへ崩すかを、毎回の `Math.random()` だけに任せない。

- 1プレイごとに `physicsSeed` を持つ。
- 軽量な疑似乱数関数を用意する。
- 同じステージ、同じseed、同じ入力なら、同じ砂崩れになることを目標にする。
- `physicsSeed` はランキングへ送らない。
- debug時だけ確認できるようにする。

## 7-8. 地形用の画面外Canvas

地形を毎フレーム全セル描画しない。

```js
const terrainCanvas = document.createElement('canvas');
```

- 論理サイズ320×960で作る。
- `imageSmoothingEnabled = false` を使う。
- 初期化時に全地形を描く。
- 砂を削る、崩す時だけ変更範囲を描き直す。
- メインCanvasでは、`cameraY` の表示範囲だけ `drawImage` する。
- DPR3の巨大な地形Canvasを必須にしない。

## 7-9. PR4の性能基準

- 最も砂が多いステージで30fps未満にならない。
- 連続スワイプ中に入力が明らかに途切れない。
- 1回の砂更新で新規オブジェクトを大量生成しない。
- 10回リトライして地形Canvas、配列、イベントが増え続けない。
- パーティクルは100個以内。
- 砂の変更範囲外を毎回描き直さない。

## 7-10. PR4の合格条件

- 現状より階段状の縁が細かい。
- 砂の小さな段差で🚬が長時間止まりにくい。
- 砂がゴール、🚬、仕掛けの中へ生成されない。
- 砂の量が、削除分と世界外落下分を除き勝手に増減しない。
- 固定壁を削れない。
- スクロール後も削る位置と表示位置が一致する。
- PR3のボール物理と終了判定を壊していない。

## 7-11. PR4の戻し方

- 既存48×144版を同じPR内で削除する前に、変換関数と比較テストを完成させる。
- 新旧切替用の開発定数はPR検証中だけ許可する。
- mainへ入れる時は採用方式1つに整理する。

# 8. PR5: 10ステージの一巡方式・個別化・公平性

## 8-1. 目的

同じステージが続く、特定ステージだけしか出ないように感じる問題をなくす。10ステージを本当に違う遊びにし、共通ランキングで比較できる範囲へ難易度をそろえる。

## 8-2. ステージ一巡方式

単純な `Math.random()` で毎回1個を選ぶ方式をやめる。

```js
let stageBag = [];
let lastStageId = null;
```

仕様:

- 1〜10をFisher-Yatesで並べ替える。
- 1個ずつ取り出す。
- 10個を使い切るまで重複しない。
- 一巡後に再度並べ替える。
- 新しい一巡の先頭が前回最後と同じなら入れ替える。
- 同じタブ内では `sessionStorage` に残り順を保存してよい。
- 保存値が壊れている場合は安全に作り直す。
- ランキングへステージIDを送らない。

## 8-3. ステージデータの個別化

`makeStage(name, shortName, variant)` だけで全ステージを生成する方式を終了する。

共通外壁など、本当に共通な部分だけヘルパーで共有する。各ステージは次を個別に持つ。

```js
{
  id,
  revision,
  name,
  shortName,
  difficulty,
  spawnClusters,
  sandRects,
  wallRects,
  initialCarves,
  traps,
  mechanisms,
  goal,
  safeRoute,
  notes
}
```

ステージ名は現在の10種類を維持する。

1. 三つ道
2. 左安全路
3. 中央ゲート
4. 右高得点路
5. 二段バー
6. 広い受け皿
7. 細い通路
8. 危険サンド
9. 回転障害物
10. 総合

## 8-4. 各ステージの役割

### 三つ道

上層で左・中央・右へ分かれ、中層で再判断し、下層で合流する基準ステージ。

### 左安全路

左に広い安全路、右に高得点だが危険なルートを置く。安全路だけでも20個を狙える。

### 中央ゲート

中央の開閉ゲートを主役にする。ゲート下へ十分な受け皿を置き、0〜5個で止まる配置を禁止する。

### 右高得点路

右側へ黒🚬を導きやすいが、ローターと危険ゾーンで損失の可能性を作る。左側へ救済路を置く。

### 二段バー

中上層と中下層にバーを1本ずつ置く。バー上へ永久に溜まらず、端から落下できる余白を確保する。

### 広い受け皿

ゴール前の受け皿を広くする。ただし、放置で20個届かず、上層の砂を削る必要は残す。

### 細い通路

精密な砂削りを求めるが、ボール直径と余白を含む最低通路幅を守る。左右に救済経路を残す。

### 危険サンド

危険ゾーンを多めに置くが、危険を避ける安全路を必ず1本残す。通常🚬まで大量喪失する配置を禁止する。

### 回転障害物

ローターの接触位置とタイミングを使う。ローターを避ける補助路を残し、全滅を避ける。

### 総合

バー、ゲート、ローター、危険ゾーン、分岐を組み合わせる。全要素を入れることより、理解できる順番で出すことを優先する。

## 8-5. ステージ自動検査

最低限、次を検査する。

- `STAGES.length === 10`
- IDが1〜10で重複しない。
- 名前とshortNameが空でない。
- すべての座標が世界内。
- 仕掛けは5個以内。
- トラップは6個以内。
- ゴールが固定壁や危険ゾーンと重ならない。
- 初期🚬が固定壁、砂、危険ゾーン、仕掛けと重ならない。
- 世界幅を完全に横断する固定壁がない。
- ゴール直上140pxが固定壁で大きく塞がれていない。
- 最終通路幅が `BALL_RADIUS * 2 + 4` 以上。
- 水平バーがゴール入口を長時間完全封鎖しない。
- `safeRoute` の各区間が固定壁・危険ゾーンで完全封鎖されていない。
- 黒🚬だけが危険側へ強制される配置になっていない。

検査失敗時は、そのステージを通常選択へ入れず、開発時にはエラーとして扱う。

## 8-6. debug用ステージ指定

通常公開では隠し、debug時だけ次を使えるようにする。

```text
?debug=1&stage=3&seed=1234
```

- `stage` でステージを固定。
- `seed` で砂崩れ・初期差分を再現。
- 通常プレイではURL指定を無視する。

## 8-7. 共通ランキングの公平性

ステージ別ランキングと補正点は、ユーザー承認なしで追加しない。

まず配置を調整し、次を目標にする。

```text
各ステージの成功率: 40〜75%
各ステージの成功時中央値: 25〜45秒
各ステージのスコア中央値: 全体中央値の±10%以内
20個へ届かない詰み発生率: 5%未満
放置だけで20個到達: 0件
```

測定は同じ公開候補版、同じ操作説明、同じテスター条件で行う。

各ステージ最低10回、合計100回を初回基準とする。可能なら複数人で確認する。

差が±10%に収まらない場合:

1. ゴール幅、危険位置、砂量、仕掛け速度を調整する。
2. それでも収まらない場合、共通ランキングを維持するか、補正を入れるかをユーザー判断へ戻す。
3. 自動でステージ補正点を導入しない。

## 8-8. PR5の合格条件

- 最初の10プレイで10種類が1回ずつ出る。
- 同じステージが連続しない。
- リトライでも次のstageBagを使う。
- ページ内再読み込み後も同じタブなら残り順を復元できる。
- ステージ10だけが続く問題を再現できない。
- 10ステージが地形・分岐・仕掛け・危険の役割で見分けられる。
- 全ステージで20個到達を狙える。
- 共通ランキングの中央値差が目標内。
- ステージ別の追加送信項目をRPCへ入れていない。

# 9. PR6: UI・操作説明・アクセシビリティ

const SCROLLBAR_DRAW_W = 24;

- 画面より上に🚬がいる場合は上向き通知。
- 画面より下に🚬がいる場合は下向き通知。

## 9-3. 初回操作説明

初回プレイだけ、ゲーム開始後に短い説明を順番に出す。

```text
左の黄色いバーで上下を見られます
砂の上をなぞって道を作ります
20個届けると成功です
```

- 1メッセージ1.5〜2秒程度。

- 表示済みはlocalStorageへ保存してよい。
- ルール画面から再表示できるようにする。

## 9-4. HUD

常時見せる情報を次へ整理する。

- 残り時間
- 届けた数 / 20
- activeな🚬の残数
- 失った数
- ステージ番号と短い名前
- リタイア

同じ内容を上下へ重複表示しない。

## 9-5. 終了理由

`resultData.endCause` を利用し、結果画面へ短い理由を追加する。

```text
時間切れ
残りを全部届けても20個に届かない
すべての🚬が処理済み
ゴールより下へ落下
長時間進展なし
リタイア
```

公開上の成功・失敗・リタイアと指定コメントは維持する。

## 9-6. 結果画面の導線

結果画面に次を置く。

- もう一度
- ホームへ戻る
- 結果をシェア
- 他のゲームで遊ぶ

「もう一度」は現在どおりREADYから即再挑戦する。「ホームへ戻る」で名前変更とルール確認ができる。

## 9-7. シェアの反応

画面内の短い通知を追加する。

- シェアしました
- シェア文をコピーしました
- コピーできませんでした

共有キャンセルはエラー扱いにせず、通知を出さなくてもよい。

## 9-8. 名前とランキングの説明

名前入力付近かルール画面に、次を短く表示する。

```text
入力した名前と配達スコアは公開ランキングに送られます。
```

個人情報を入力しないよう、10文字以内のニックネームを案内する。

## 9-9. 色以外の見分け

色覚差に備え、🚬の外周へ小さい形を付ける。

```text
白っぽい: ○
赤: ▲
青: ●
黒: ■
```

文字や絵文字を邪魔しない位置へ描く。

## 9-10. 画面と安全領域

- `safe-area-inset-top` と `safe-area-inset-bottom` を考慮する。
- 320px幅でもHUDとリタイアが押せる。
- 横画面では「縦向きで遊んでください」を出す。
- 横画面でも結果画面やホームへ戻れる。
- リンクの長押しは必要以上に妨げない。
- ボタンの実当たり範囲は44px以上を基本にする。

## 9-11. 動きを減らす設定

`prefers-reduced-motion: reduce` の場合:

- 危険ゾーンの点滅を弱める。
- 成功フラッシュを短く、または静止表示にする。
- ボタンの移動を弱める。
- ゲーム物理そのものは変えない。

## 9-12. 音

音は完成必須ではないが、追加する場合は次を守る。

- 外部音源を使わずWeb Audioで短い音を作る。
- 届いた時、失った時、成功時だけ鳴らす。
- 最初のユーザー操作後にだけ初期化する。
- オン・オフを用意し、設定を保存する。
- 音を切っても情報が欠けない。

## 9-13. PR6の合格条件

- 初見で左バーを操作できる。
- 画面外に🚬が残っていることが分かる。
- active残数が分かる。

# 14. 完成の定義

「たばコン」は、次をすべて満たした時だけ完成とする。

1. 仕様書とコードが一致している。
2. 物理が固定間隔で進む。
3. 🚬同士が自然に衝突する。
4. 平らな場所で震え続けない。
5. 見た目と当たり判定がほぼ一致する。
6. 高速移動で地形を明らかに抜けない。
7. 砂の階段感が現状より小さい。
8. 砂が🚬、ゴール、仕掛けの中へ移動しない。
9. 10ステージを一巡するまで重複しない。
10. 同じステージが連続しない。
11. 10ステージが地形と仕掛けで区別できる。
12. 全ステージで20個到達を狙える。
13. 共通ランキングで極端なステージ有利がない。
14. 動かせる🚬がない状態で待たされない。
15. 20個到達時点で結果が固定される。
16. 結果は一度だけ確定する。
17. ランキング送信は1プレイ1回。
18. 古い通信結果が次のプレイを上書きしない。
19. 通信失敗でも結果、再挑戦、シェアが使える。
20. スクロールバーを初見で操作できる。
21. 画面外の🚬分布が分かる。
22. 失敗理由が分かる。
23. iPhone SE相当で横スクロールなく遊べる。
24. iPhone 11 Proで30fps未満へ長時間落ちない。
25. iPhone 17 ProとiPad Pro 2018で表示が崩れない。
26. 連続リトライ10回で処理が増殖しない。
27. 30分連続プレイでメモリが一方向に増え続けない。
28. 通常公開時にdebug機能が露出しない。
29. secret key、service_role key、直接INSERTがない。
30. Supabase、Codeberg、実験場、詳細ランキングが一致する。
31. 公開コミット、CLIENT_VERSION、実機結果、ロールバック先が記録されている。
